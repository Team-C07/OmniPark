# TCS — Persistenza: segnalazioni, letture delle targhe e verifiche

- **Task:** OMP-34 (issue #6). Metodo: category partition.
- **Oggetto:** le funzioni di accesso di `src/persistence/accessoDati/segnalazioniVerifiche.ts`.
- **Fonti dell'esito atteso:** sequence diagram e casi d'uso indicati per ogni funzione (inventario del piano approvato); vincoli dello schema; `docs/rad/requisiti.md`; `docs/rad/vincoli_dominio.md` §2; statechart `SCD_3`; codici di errore di `docs/test/cp_persistenza_base.md`.
- **File di test:** `src/persistence/accessoDati/segnalazioniVerifiche.db.test.ts` (eseguito da `npm run test:db`).

Le letture delle targhe non hanno una tabella: della lettura ANPR la segnalazione conserva targa e data e ora (D1 del piano).

## 1. Tracciabilità

Ogni frame riporta un solo riferimento, scelto in quest'ordine: un requisito dell'Elenco (`RF_…`, `NRF_…`) se il suo testo copre davvero il comportamento; altrimenti il vincolo di dominio `VD_<n>` (`docs/rad/vincoli_dominio.md` §2); altrimenti `SCHEMA` se il frame verifica un vincolo specifico dello schema.

Nome del test: `<riferimento> · <frame> · <descrizione> → <esito>`, per esempio `RF_OP_3 · TF-SV-25 · presa in carico di una segnalazione già presa → false`.

## 2. Funzioni verificate (firme)

Il primo parametro è sempre l'esecutore (`Esecutore = Pool | PoolClient`, da `./esecutore`); nei test è il client della transazione del test. Gli id sono `number`; gli istanti `Date`. Gli errori sono `ErroreDominio` con il `codice` indicato (`./errori`).

```ts
type StatoSegnalazione = "APERTA" | "PRESA_IN_CARICO" | "CHIUSA";
type Motivo = "SOSTA_ASSENTE" | "SOSTA_SCADUTA" | "TARGA_NON_CORRISPONDENTE";
type Esito = "SOSTA_IRREGOLARE_ACCERTATA" | "NON_CONFERMATA";
type EsitoVerifica = "CONFORME" | "NON_CONFORME";
type SegnalazioneMappa = {
  id; stalloId; numeroStallo; latitudine; longitudine; stato: StatoSegnalazione;
  motivo: Motivo | null; targaRilevata: string | null; dataEOraDellaLettura: Date | null;
  ausiliarioId: number | null; ultimaModifica: Date;
};
type DettaglioSegnalazione = SegnalazioneMappa & {
  tipoDiStallo; enteId: number; dataEOraDellaPresaInCarico: Date | null; esito: Esito | null;
  dataEOraDellaChiusura: Date | null; verificaDelPermessoId: number | null;
  assegnatario: { id: number; nome: string; cognome: string } | null;
};

esisteSegnalazioneNonChiusa(es, targa: string): Promise<boolean>;
creaSegnalazioneDaLettura(es, dati: { stalloId; targa; dataEOra: Date; motivo: Motivo }): Promise<number>; // nasce APERTA
segnalazioniNonChiuseDellEnte(es, enteId: number): Promise<SegnalazioneMappa[]>;  // APERTA e PRESA_IN_CARICO, ordinate per id
segnalazioniModificateDopo(es, enteId: number, istante: Date): Promise<{ segnalazioni: SegnalazioneMappa[]; cursore: Date | null }>;
// segnalazioni dell'ente in qualsiasi stato con ultima_modifica > istante, ordinate per id; cursore = max(ultimaModifica), null se nessuna
permessiDaVerificare(es, enteId: number): Promise<{ sostaId; stalloId; tipoDiStallo; latitudine; longitudine; targa: string }[]>;
// soste ATTIVA con dichiarazione e foto, in stalli DISABILI o ROSA dell'ente, senza verifica; ordinate per id della sosta
dettaglioSegnalazione(es, id: number): Promise<DettaglioSegnalazione | null>;
prendiInCarico(es, id: number, ausiliarioId: number, dataEOra: Date): Promise<boolean>;
// solo se APERTA: assegna e porta a PRESA_IN_CARICO; false se non è (più) APERTA o non esiste
chiudiSegnalazione(es, id: number, ausiliarioId: number, esito: Esito, dataEOra: Date): Promise<boolean>;
// se APERTA (la assegna a chi chiude) o PRESA_IN_CARICO dallo stesso ausiliario: CHIUSA con esito e data; false altrimenti
contaSegnalazioniPreseInCarico(es, ausiliarioId: number): Promise<number>;
registraVerifica(es, dati: { sostaId; ausiliarioId; esito: EsitoVerifica; dataEOra: Date }): Promise<number>;
creaSegnalazioneDaVerifica(es, dati: { verificaId; stalloId; ausiliarioId; dataEOra: Date }): Promise<number>;
// nasce CHIUSA, esito SOSTA_IRREGOLARE_ACCERTATA, assegnata all'ausiliario, senza dati di lettura
```

Ordinamento degli elenchi: `segnalazioniNonChiuseDellEnte` e `segnalazioniModificateDopo` per id della segnalazione; `permessiDaVerificare` per id della sosta. Gli id sono unici, quindi non serve uno spareggio.

`prendiInCarico` e `chiudiSegnalazione` sono atomiche sullo stato (un solo `UPDATE … WHERE stato …`). La segregazione per ente (VD_18) resta al sottosistema (piano approvato).

## 3. Ambiente

- Database di test riportato allo stato noto da `preparaDatabaseDiTest()` nel `beforeAll`; ogni test in una transazione annullata (`iniziaTransazioneDiTest()` / `annullaTransazioneDiTest()`), con il client come esecutore.
- Istante del dataset per `ultima_modifica` di tutte le segnalazioni: `2026-11-15 08:00:00+01`. Istante di prova `I` = `2026-11-20 09:00:00+01`. Permesso «completo»: dichiarazione `Dichiaro di esporre il permesso previsto per lo stallo` e foto di 1024 byte.
- Le soste `ATTIVA` con permesso richieste dai frame si inseriscono con SQL nella transazione del test (colonne sotto), con orari `I` → `2026-11-20 10:00:00+01` e pagamento `PAGATA` (stallo `ROSA`) o `GRATUITA` (stallo `DISABILI`).

Note sui riferimenti:

- TF-SV-01…04, 06, 07: VD_16 (al più una segnalazione non chiusa per targa); una targa con sole segnalazioni chiuse può averne una nuova.
- TF-SV-32: la chiusura diretta di una segnalazione `Aperta` è prevista da `SCD_3` (`Aperta --> Chiusa : chiusura / assegnaAusiliario(), registraEsito()`), da `UC_OP_4` (Regole di dominio e passo 4) e da `SD_OP_4` (`opt [la segnalazione è Aperta] 4.1: assegnaA`).
- TF-SV-19…22: `permessiDaVerificare` comprende solo le soste `ATTIVA`, non le `SCADUTA`: RF_OP_2 parla di stalli «occupati da una sosta attiva», `vincoli_dominio.md` §1 definisce il permesso da verificare come una sosta «in stato `Attiva`» senza verifica, e `UC_OP_5` 2.a1 dice che con la sosta `Scaduta` o `Terminata` «non c'è più nulla da verificare».
- TF-SV-15…18: la mappa delle segnalazioni con le sole variazioni (RF_OP_1). Il cursore ha lo stesso limite descritto in `cp_persistenza_stalli_tariffe.md` §6.
- TF-SV-30, 31, 37, 45, 46: vincoli dello schema (chiave esterna, `segnalazione_date_ordinate`, valori ammessi).
- TF-SV-38…41: il conteggio serve a non disattivare un ausiliario con segnalazioni prese in carico (VD_19, `UC_ADM_2` 3.a2).
- TF-SV-48, 50: VD_13 (la segnalazione nasce solo da una verifica non conforme ed è assegnata a chi l'ha registrata); TF-SV-49: una verifica genera al più una segnalazione (associazione «genera» 0..1, vincolo `segnalazione_una_per_verifica`).

## 6. Nota sul cursore e regole lasciate ai sottosistemi

Il cursore di `segnalazioniModificateDopo` ha gli stessi limiti descritti in `cp_persistenza_stalli_tariffe.md` §6. Precisione: il cursore è un `Date` di JavaScript, al millisecondo, mentre `ultima_modifica` in PostgreSQL è al microsecondo; nella richiesta successiva la stessa segnalazione può tornare una seconda volta, ma non va mai persa. Il sottosistema Segnalazioni scarta i duplicati per id.
